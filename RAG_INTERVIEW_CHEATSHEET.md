# 📋 RAG Interview Cheatsheet

**Шпаргалка: как отвечать на технические вопросы по RAG на собеседовании**

---

## 1. «Как ты подбирал размер чанка (chunk size)?»

**Ответ по структуре: Проблема → Эксперименты → Вывод**

> «Я исходил из природы документов и модели эмбеддингов. `text-embedding-3-small` принимает до 8191 токенов, но оптимальная семантическая единица — абзац или несколько предложений. Начал с 1000 символов и overlap 200.
>
> Проверял качество на тестовых вопросах: слишком маленькие чанки (300 символов) теряют контекст предложения, слишком большие (2000+) "размывают" вектор — запрос "режим работы" находит чанк про больничный, потому что они в одном блоке.
>
> 1000 символов / overlap 200 — баланс между точностью и контекстом. Разделители в приоритете: `\n\n` → `\n` → `. ` — режем сначала по абзацам, не по середине предложения.»

**Ключевые тезисы:**
- Chunk size зависит от документа (инструкция vs книга) и embedding-модели
- Overlap нужен, чтобы не потерять смысл на границе чанка
- Качество измеряется на реальных вопросах, не интуитивно

---

## 2. «Как решал проблему потери контекста диалога?»

**Ответ:**

> «RAG по умолчанию stateless — каждый запрос независим. Проблема: пользователь спрашивает "а что насчёт удалёнки?" после вопроса про режим работы — без контекста модель не понимает о чём речь.
>
> Решение: использую `ConversationalRetrievalChain` из LangChain. Перед retrieval история последних N сообщений подаётся в `condense_question_prompt` — LLM переформулирует вопрос с учётом контекста (например, "а что насчёт удалёнки?" → "каков порядок удалённой работы в компании?"). Затем идёт обычный vector search.
>
> История хранится в Supabase, подгружается при каждом запросе. N=5 — баланс между памятью и размером промпта.»

**Ключевые тезисы:**
- `ConversationalRetrievalChain` + `condense_question` решают проблему coreference
- Память хранится в БД, не в памяти процесса (работает при рестарте)
- N сообщений — параметр, который нужно тюнить под use-case

---

## 3. «Как оценивал качество RAG?»

**Ответ:**

> «Использовал три уровня оценки:
>
> **1. Retrieval quality:** проверял, попадает ли правильный чанк в Top-K. Для тестового документа составил 10-15 вопросов с известным ответом и смотрел precision@5 — сколько из 5 возвращаемых чанков реально релевантны.
>
> **2. Answer quality (вручную):** брал ответы бота и проверял: содержит ли ответ правильную информацию, нет ли галлюцинаций, корректна ли ссылка на источник.
>
> **3. Failure cases:** специально задавал вопросы, ответа на которые нет в документах — проверял, признаёт ли модель незнание или выдумывает.»

**Можно упомянуть продвинутые инструменты:**
- RAGAs (библиотека для автоматической оценки: faithfulness, answer relevancy, context recall)
- LangSmith для трейсинга pipeline

## 4. «Как обеспечил масштабируемость при больших объёмах документов?»

**Ответ:**

> «Несколько решений в связке:
>
> - **Асинхронная индексация**: загрузка идёт в `BackgroundTasks` FastAPI, не блокирует API. Статус в БД — клиент может polling'ом проверять готовность.
> - **ChromaDB**: хранит векторы на диске (persistent mode), не в памяти. Поддерживает миллионы документов.
> - **Батчинг embeddings**: при большом количестве чанков запросы к OpenAI идут батчами по 100, чтобы не упереться в rate limits.
> - **Метаданные в ChromaDB**: каждый чанк хранит `filename`, `page_number`, `chunk_index` — это позволяет фильтровать по источнику и возвращать точную ссылку.»

---

## 5. «Почему ChromaDB, а не Pinecone/Weaviate/pgvector?»

**Ответ:**

> «Для MVP и on-premise развёртывания ChromaDB — оптимальный выбор:
> - Разворачивается одной строкой Docker, нет внешних зависимостей
> - Персистентное хранение на диске, легко бэкапить
> - HTTP API совместим с LangChain из коробки
>
> Если бы требования были enterprise-уровня (мультитенантность, SLA, managed-сервис) — рассмотрел бы Pinecone или Weaviate Cloud. Для Postgres-стека — pgvector с `halfvec` для 3072-мерных эмбеддингов. ChromaDB — это осознанный выбор под задачу, а не дефолт.»

## 6. «Как работает промпт для RAG? Что ты туда кладёшь?»

**Ответ:**

> «Промпт состоит из трёх частей:
>
> ```
> SYSTEM: Ты корпоративный ассистент. Отвечай ТОЛЬКО на основе предоставленного контекста. 
> Если ответа в контексте нет — скажи об этом.
>
> CONTEXT:
> [retrieved chunk 1 — filename.pdf, стр. 3]
> ...текст...
>
> [retrieved chunk 2 — filename.pdf, стр. 7]
> ...текст...
>
> ИСТОРИЯ ДИАЛОГА:
> User: предыдущий вопрос
> Assistant: предыдущий ответ
>
> USER: текущий вопрос
> ```
>
> Ключевые элементы: инструкция не галлюцинировать, контекст с метаданными источника, история.»

---

## 7. «Что такое RAG и зачем он нужен вместо fine-tuning?»

**Ответ:**

> «RAG (Retrieval-Augmented Generation) — паттерн, при котором LLM отвечает на вопрос, опираясь на динамически подгруженные документы, а не только на параметры модели.
>
> **Vs Fine-tuning:**
> - Fine-tuning "запекает" знания в веса — дорого (обучение), знания устаревают
> - RAG обновляется мгновенно — добавил документ, он сразу доступен
> - RAG прозрачен: видно, на каком фрагменте основан ответ (аудитабельность)
> - Fine-tuning эффективнее для стиля и формата ответа, RAG — для фактических знаний
>
> На практике: RAG для корпоративных знаний, fine-tuning для персонализации голоса.»

---

*Совет: на собеседовании говори конкретно — называй параметры (1000/200, Top-5, N=5 истории), упоминай компромиссы. Это показывает, что ты принимал осознанные инженерные решения, а не просто копировал туториалы.*
